## 一、简历项目经历（推荐 4 条）

### 360° 全景视频自动运镜 Agent ｜ 独立开发 ｜ 2026.09 – 至今

> **技术栈**：Python · PyTorch/CUDA · OpenCV · SciPy · FastAPI · Docker
> **代码量**：8508 行源码 / 5404 行测试，**533 项单元测试全绿**，18 次提交

**1. 设计球面几何层并解决全景视频的「跨接缝跟踪」难题**

针对 ERP（等距柱状投影）视频中目标从图像右缘移出、左缘进入导致跟踪器
丢失 ID 的问题，在**提升空间（unwrapped yaw）**中建模：滤波前将周期量
从 S¹ 提升到 ℝ，使 ±180° 处的跳变转化为正常的连续运动。配套实现球面
Kalman 滤波、大圆距离数据关联、环形 padding 检测框合并。在受控序列上
实现 200 帧连续绕圈（5 圈）**零 ID 重建**；与 py360convert 逐像素对拍，
几何误差 < 1e-5°。

**2. 提出 Panorama Scene Graph（PSG）—— 面向 LLM 的双视图结构化表示**

将全景视频解耦为**符号层**（供 LLM 语义规划：track_id / 语义描述 /
球面统计量）与**数值层**（供优化器：逐帧 `yaw/pitch/宽/高/conf`），
通过 `track_id` 严格对齐。**关键设计：EditDSL 的 pydantic schema 中不存在
任何坐标字段** —— LLM 只能引用 track_id，从而保证它输出的是**可校验的
约束**而非不可校验的解。30 秒视频的 LLM 视图约 200 字符/条轨迹。

**3. 实现基于约束优化的虚拟相机轨迹求解器**

将「主体居中 / 三分法构图 / 轨迹平滑 / 角速度上限」建模为可微目标函数，
在 unwrapped 角度空间用 L-BFGS-B 求解。自研 4 个递进 baseline
（CenterCrop / SaliencyGreedy / SaliencySmooth / Ours）做量化对比：

| | 居中率 | 角速度合规 | 峰值速度 |
|---|---|---|---|
| SaliencyGreedy（逐帧贪心） | 100% | 64% | 97°/s |
| SaliencySmooth（+低通滤波） | 100% | 58% | 57°/s |
| **Ours** | **100%** | **83%** | **46°/s** |

其中 SaliencyGreedy 的平滑度恰等于输入噪声基准，**实验上证明了
「逐帧最优 ≠ 全局最优」**。

**4. 在 4GB 显存约束下完成端侧工程与部署**

针对 RTX 3050 Laptop 的显存约束（实测可用 3306MB），实现**子进程模型隔离
+ 显存预算调度**（`torch.cuda.empty_cache()` 不可靠，唯一可靠的释放是
进程退出）+ OOM 自动降级。YOLO11n 实测峰值 64.7MB / 12.4ms。搭建
FastAPI 异步服务与单文件 Web Demo（自然语言指令 → 实时进度 → 成片播放），
端到端 30 帧约 15 秒。

## 三、⚠️ 必须主动说明的局限

**在被问到之前主动讲，比被问出来好。**

1. **数据集是静态全景图，不是视频**
   因此「跟踪质量」是在**受控合成序列**上验证的（真实实例形状 +
   `np.roll` 模拟运动），而非真实视频。真实视频上未验证。

2. **没有 Pano2Vid 的人工运镜 GT**
   因此**无法**做论文级的 DTW 轨迹对比。轨迹质量只用了
   平滑度 / 居中率 / 角速度合规这类可自洽计算的指标。

3. **显著性用的是弱监督**
   无语动仪 GT（Wild360 等数据集许可不明确），改用语义分割 mask 的
   前景类作代理。**这是弱标签，不是真正的显著性标注**。

4. **构图质量没有显式建模**
   实测发现系统会选「近距离的大建筑」作为主体，画面被占满——
   因为选择依据只有「显著性 + 尺寸」，缺审美判断。改进方向是把
   构图规则（避免主体角尺寸过大）写进目标函数。

5. **LLM 规划默认走降级路径**
   Demo 中 `use_llm=False`，实际跑的是纯优化器兜底方案。
   真实 LLM 规划的通路已实现并有 24 项测试覆盖，但未在成片上做
   A/B 对比。

## 四、面试高频问题

### Q1：ERP 投影的本质问题是什么？

ERP 把球面按经纬度**线性**映射到图像坐标。问题在于 x 方向每像素对应的
球面弧长正比于 `cos φ` —— 赤道处一个像素对应最大弧长，越往高纬越小。

**面积畸变因子是 `1/cos φ`，在极点发散**：极点这个**单点**被展开成了
整条边。

**推论**：任何在 ERP 上做的池化、卷积、IoU、距离度量，都建立在非均匀
采样上，必须用 `cos φ` 做立体角加权。我项目里所有显著性积分和球面 IoU
都做了这个加权。

### Q2：你怎么处理跨 ERP 边界的跟踪？

三层：

- **状态空间**：yaw 在 S¹ 上，滤波前用 `np.unwrap` 提升到 ℝ，
  输出时再 wrap 回 [-180, 180)。这样 ±180° 处没有跳变。
- **数据关联**：用大圆距离而非像素距离，天然 wrap-aware。
- **特征域**：水平方向做 circular padding，让卷积/算子看到接缝的连续性。

**最关键的验证**是消融：跨边界的序列上提升巨大，不含边界的序列上
无差别——这证明增益来自几何建模而非其他因素。

### Q3：为什么不让 LLM 直接输出相机轨迹？

**因为 LLM 输出的是约束还是解，决定了系统能不能自我校验。**

（1）LLM 没有度量几何的概念，输出的角度值无物理意义
（2）30fps × 15s = 450 个连续值，token 成本高且必然前后矛盾
（3）拿到一串角度，我们**没有任何自动手段**判断它对不对

我的做法是让 `EditDSL` 的 pydantic schema 里**根本没有 float 坐标字段**，
LLM 只能引用 `track_id`。这样它输出的每条信息都可校验：track_id 存在吗？
景别与 FOV 自洽吗？不合法就带着错误信息重试，重试耗尽则降级到纯优化器。

**这是类型系统在架构层面的应用，不是 prompt 工程。**

### Q4：4GB 显存上你怎么做工程？

关键认知是**实测可用只有 3306MB**（桌面合成占用约 790MB，而且
`nvidia-smi` 的 used 口径比 `mem_get_info` 大，不能混用）。

手段：
- **子进程模型隔离** —— `torch.cuda.empty_cache()` 只把缓存标记为可复用，
  不保证归还驱动。唯一可靠的释放是**进程退出**
- 全部 FP16，输入 ≤ 640p
- `vram_probe.py` 实测每个模型的峰值，做成预算表
- **OOM 一键切 CPU**，保证 Demo 永不挂

对比 Insta360 的 1-2ms/帧：要诚实——那是专用 4nm NPU + 更小的输入分辨率，
我是在通用 GPU 上的通用方案，量级差异合理。

### Q5：这个项目里最难的 part 是什么？

**不是实现，是评测。**

全景运镜没有公认指标：普通 IoU 在 ERP 上物理意义是错的；而"哪个运镜
更好看"没有客观标注。

我最终用了三类指标（球的 Success/Precision、轨迹的平滑度/居中率/
角速度合规、以及自建的 4 个 baseline），并且在这过程中**三次发现
「拿错了尺子」**：

1. 用像素距离衡量球面量 → 高纬系统性高估
2. 用 jerk（三阶差分）衡量二阶优化目标 → 量纲不随帧率可比、与目标不一致
3. 用整条拼接轨迹衡量连续运动 → **把「切镜」算成了「剧烈运动」**，
   峰值虚高 49 倍

第 3 个最有代表性：指标显示 2195°/s 而配置上限 45°/s，我一度以为
求解器失控，**连续扫了 max_iter 200→4000 结果完全一样**，才意识到
该怀疑的是指标本身。修正后峰值是 46°/s，**正好贴着配置上限**——
说明约束一直在正常工作。

这段经历让我理解了：**在本项目里，「怎么衡量」和「怎么做」同等重要。**

### Q6：你的方案和 Insta360 的 Auto Frame / PanoMind 有什么关系？

- **Auto Frame** 是启发式/规则 + 检测最大化的工程方案
- **PanoMind** 是端到端学习的模型化版本（30+ 类场景、1 万小时+ 数据），
  跑在端侧三芯架构上，三大能力是高光识别、虚拟相机运动生成、
  叙事逻辑判断
- **我的方案**是一条**可解释、无需大规模训练数据**的替代路线：
  VLM 做语义 + LLM 做规划 + 经典约束优化做轨迹求解，可自然语言交互、
  每步可解释、不需要 1 万小时数据

**局限**：上限受感知精度限制；有 API 延迟与成本，不适合端侧实时；
构图规则是人工先验而非学到的审美。

### Q7：如果把你的方案放到端侧，主要瓶颈是什么？

三个：
1. **VLM/LLM 依赖云端** —— 这是最大的瓶颈。端侧要跑得换小模型或蒸馏
2. **经典优化是迭代求解的** —— L-BFGS-B 在我的笔记本上单镜头约
   0.2 秒，但那是 10-30 帧的量级；实时（30fps）需要改成增量式求解
3. **实例提取 262ms/帧** —— 纯 CPU，对离线剪辑够用，实时不够

**但也要说清**：本项目定位是**离线成片**而非实时预览，这些延迟
在目标场景下是可接受的。若要做实时取景，思路完全不同
（那更接近 VLM 的推理路径）。
