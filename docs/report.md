# PanoDirector：360° 全景视频的自动运镜 Agent

**技术报告** ｜ 2026.09

---

## 摘要

本文介绍 PanoDirector，一个将自然语言指令翻译为 360° 全景视频运镜方案的
端到端系统。系统由四层构成：**球面几何层**、**感知层**、**结构化表示层
（Panorama Scene Graph）**、**Agent 层（LLM 规划 + 约束优化 + 渲染）**。

核心论点有三：

1. **周期量的处理应发生在数据进入系统的边界。** yaw 生活在 S¹ 上，
   而下游所有算法（滤波、优化、求导）都只理解 ℝ。本项目在数据入口处
   做一次提升（unwrap），此后各层均可当作普通线性量处理。这一原则在
   跟踪器、检测框合并、光流、轨迹求解四处被独立应用。

2. **LLM 应当输出约束而非解。** 系统通过 pydantic 的类型系统强制
   ——EditDSL 中没有任何坐标字段——使 LLM 只能引用 `track_id`，
   从而保证其输出**可校验、可拒绝、可兜底**。

3. **「怎么衡量」与「怎么做」同等重要。** 本项目在开发过程中三次遇到
   「指标选错导致误判系统有缺陷」的情况（§5.3），每次都差点走向
   错误的修复方向。

**代码规模**：8508 行源码 / 5404 行测试，533 项单元测试全部通过。

## 1. 引言

### 1.1 问题与动机

360° 相机（如 Insta360 系列）拍摄的等距柱状投影（ERP）视频包含完整
视场，但**观看者只能看到其中一小块**。传统的后处理需要人工逐帧选择
视角，与拍摄时长成线性关系——一段 10 分钟的素材可能对应数小时的
剪辑工作。

Insta360 在 2026 年发布的 **PanoMind** 端侧模型给出了工业界答案，
其三大能力是：高光识别、虚拟相机运动生成、叙事逻辑判断。
配套的 Moments Pro 支持自然语言驱动的一站式剪辑。

本项目的目标是探索一条**可解释、无需大规模训练数据**的替代路线：
用 VLM 做语义理解、LLM 做剪辑规划、经典约束优化求解相机轨迹。

### 1.2 为什么是「约束」而不是「解」

一个自然但错误的想法是：让 LLM 直接输出相机轨迹。

**它错在可校验性上。**

| | 约束（constraint） | 解（solution） |
|---|---|---|
| 例子 | "拍 track_id=3，中景" | "相机在 yaw=37.5°" |
| 可校验 | ✅ 检查 id 是否存在、FOV 是否在区间 | ❌ 无从判断对错 |
| 出错时 | 可拒绝、可重试、可降级 | 只能靠肉眼看出来 |
| token 成本 | 几十 | 30fps×15s = 450 个浮点数 |

本项目的 `EditDSL` schema 中**不存在任何表示坐标的 float 字段**。
这不是靠 prompt 里写"请不要输出坐标"，而是让 LLM **根本没有字段可填**
（`extra="forbid"` 保证它捏造坐标字段会被直接拒绝）。

## 2. 相关工作

### 2.1 全景视觉的三大鸿沟

Insta360 研究院的全景视觉综述（arXiv 2509.04444）指出从透视到全景的
三个根本差异：

1. **两极严重几何畸变** —— 面积畸变因子 `1/cos φ` 在极点发散
2. **ERP 非均匀采样** —— 赤道处 10 像素 ≈ 0.3°，高纬处 10 像素 ≈ 3°
3. **周期性边界连续性** —— ERP 左右边界是同一条经线

该综述把方法分为两族：**Distortion-Aware**（直接在 ERP 上建模，适合
全局语义任务）与 **Projection-Driven**（投影到 Cube/Tangent，适合
几何敏感任务）。

**本项目的方法分布**：几何层与跟踪采用 Distortion-Aware（在球面角度
上计算），检测提供 Cube 投影的对照实现，轨迹求解在 unwrapped 角度
空间进行。

### 2.2 自动运镜

Pano2Vid（ACCV 2016）首次形式化"从 360° 视频自动生成普通视场视频"的
问题，并提供了唯一公开的**人工运镜轨迹标注**。其核心观察是：
逐帧选择最显著区域会产生抖动的轨迹，需要考虑时序一致性。

本项目复现了这一问题：`saliency_greedy` baseline 的居中率 100%
（每帧都精确对准）但平滑度**恰等于输入噪声基准**，实验上证明了
"逐帧最优 ≠ 全局最优"。

### 2.3 与本项目的关系

DA360（全景深度适配）用 **circular padding** 消除 ERP 接缝、
**learnable shift** 处理尺度不变性。本项目受其启发，在多处采用
同构的处理：跟踪器的 yaw 提升、检测框的接缝连续坐标、光流的环形
padding、轨迹求解的 unwrapped 空间。

**这四个地方用不同数学工具，解决的是同一个问题**：
把周期性在数据边界处理一次，之后各层当普通量处理。

## 3. 方法

### 3.1 系统架构

```
输入：ERP 全景图 + 自然语言指令
  │
  ├─ L1 几何层        sphere / projection / region / camera
  │                   球面坐标、大圆距离、ERP↔透视、BFoV、球面 IoU
  │
  ├─ L2 感知层        instance / track_spherical / registry / flow / saliency
  │                   实例提取、球面 Kalman 跟踪、显存调度
  │
  ├─ L3 表示层 ★      Panorama Scene Graph
  │                   符号层（给 LLM） ⟷ track_id ⟷ 数值层（给优化器）
  │
  └─ L4 Agent 层      planner(LLM) → dsl → solver(L-BFGS-B) → render(NFOV)
  │
输出：NFOV 成片 + 可解释的决策链
```

### 3.2 球面几何层

**坐标约定**（全项目唯一真相）：

```
yaw   (λ) ∈ [-180, 180)   0° 指向 +Z，+90° 指向 +X
pitch (φ) ∈ [-90, 90]     +90° 指向 +Y（天顶）

单位向量:  x = cos φ·sin λ,  y = sin φ,  z = cos φ·cos λ

ERP 像素:  x_px = (λ+180)/360·W - 0.5     ← 整数索引即像素中心
           y_px = (90-φ)/180·H - 0.5
```

**验证**：与 py360convert 逐像素对拍，光线方向误差 < 1e-5°，
ERP 采样坐标误差 < 4e-5 像素。

**两个已修复的陷阱**：

- `sph_to_erp_pixel` 漏减 0.5 → 系统性半像素偏移（讽刺的是，模块文档里
  恰好警告了这个陷阱，测试首次运行即抓住）
- `from_erp_pixels` 的 `center_pitch` 漏加 0.5 → 往返测试中稳定表现为
  0.50px 固定偏差

### 3.3 跨接缝跟踪

**问题**：ERP 左右边界是同一条经线。目标从 x=W-1 移出会从 x=0 进入
——它从未离开视野。朴素跟踪器看到的却是 yaw 从 +179° 跳到 -179°，
像素距离达半个图像宽度，远超任何合理的关联门限。

**解法**（核心操作只有三行）：

```python
k = round((predicted_unwrapped - observed_wrapped) / 360)
lifted = observed_wrapped + k * 360
```

于是 `+179° → +181°` 在滤波器眼中只是 2° 的正常转动。

**验证**：200 帧连续绕圈（5 圈）零 ID 重建。测试中还包含**对照组**
——证明朴素做法确实会失败（wrap 后直接相减得到 358° 的假距离，
而真实大圆距离是 2°，相差 179 倍）。

### 3.4 ★ Panorama Scene Graph

**设计目标**：同时服务两个需求相反的消费者。

| | LLM | 优化器 |
|---|---|---|
| 需要 | 少 token、语义化、可读 | 全精度、逐帧、可微 |
| 视图 | 符号层 `to_llm_view()` → JSON | 数值层 `numeric_ref` → `.npz`（mmap） |
| 内容 | track_id / caption / 属性 / 球面统计量 | yaw[]/pitch[]/w[]/h[]/conf[] |
| 规模 | 约 200 字符/条 | 逐帧全精度 |

两者通过 `track_id` 严格对齐。

**为什么统计量必须与分辨率无关**：`TrackStats` 中所有量以球面角度或
秒为单位。这使 30 秒 2K 与 5 分钟 4K 的视频统计量可直接比较，
且 LLM 读到的是"角速度 45°/秒"这类有物理含义的量。

**强制隔离由测试守住**：LLM 视图中不得出现任何几何坐标字段，
也不得出现数值文件的路径。

### 3.5 轨迹优化

**问题形式化**：

```
minimize  w_center · L_center  +  w_smooth · L_smooth
        + w_velocity · L_velocity  +  w_fov · L_fov  +  w_thirds · L_thirds

L_center    主体相对光轴的偏移（大圆距离）
L_smooth    相机角加速度（二阶差分）
L_velocity  角速度超限的软惩罚
L_fov       FOV 变化率 + 与目标景别的偏差
L_thirds    三分法构图偏差
```

**为什么在 unwrapped 空间求解**：与跟踪器完全同源。若直接在
[-180,180) 上优化，相机从 179° 转到 181° 时参数上表现为 179 → -179，
梯度会认为需要跨越 358°。

**一个实测教训**：早期版本定义了 `max_angular_vel_dps=45` 却**没有实现
对应的惩罚项**，实测峰值达 253.6°/s（超限 5.6 倍）。约束声明了 ≠
约束被执行——这类缺陷在单元测试里不容易暴露（求解器确实"收敛"了），
只有把输出数据摊开看才会发现。

同样地，`motion` 参数最初**只影响初始猜测**，不影响目标函数。后果是
无论声明 `static` 还是 `follow`，优化器都收敛到"主体居中"——
static 镜头跟着主体跑，峰值角速度 120°/s。

修正后各运镜表现出应有的差异：

| 运镜 | 峰值角速度 | 跟随误差 |
|---|---|---|
| static | 0.0°/s | 10.22° |
| follow | 26.9°/s | 0.00° |
| lead | 26.9°/s | 15.23° ← 正是 `lead_offset_deg=15` |
| pan | 26.9°/s | 0.00° |

## 4. 实验

### 4.1 实验设置

**数据**：Insta360 官方 Omni360-X（CVPR 2026 AirSim360 配套），
5179 张 ERP 全景图（2048×1024），含语义 / 实例分割标注。
许可 CC-BY-NC-4.0。

**硬件**：RTX 3050 Laptop，实测可用显存 3306MB。

**⚠️ 数据约束**：该数据集是**静态全景图**，无视频序列。因此跟踪质量
在**受控合成序列**上验证（真实实例形状 + `np.roll` 环绕平移，
天然制造跨接缝场景），而非真实视频。

### 4.2 Baseline 对比

四个递进 baseline，每个增加一个组件：

| Baseline | 居中率 | 平均偏移 | 平滑 (°/s²) | 角速度合规 | 峰值速度 |
|---|---|---|---|---|---|
| `center_crop`（固定机位） | 22% | 20.94° | 0.0 | 100% | 0°/s |
| `saliency_greedy`（逐帧贪心） | 100% | 0.00° | **634.3** | 64% | 97°/s |
| `saliency_smooth`（+低通滤波） | 100% | 0.97° | 69.9 | 58% | 57°/s |
| **`ours`** | 100% | 2.32° | 92.7 | **83%** | **46°/s** |

输入噪声的角加速度基准为 **634.3 °/s²**。

**三个观察**：

1. **`center_crop` 是合格的地板线** —— 居中率仅 22%，说明后续三者
   确实做了事。

2. **`saliency_greedy` 的平滑度恰等于输入噪声基准** —— 它**完全没有
   做时序平滑**。这是"逐帧最优 ≠ 全局最优"的直接实验证据。

3. **`ours` 是权衡而非全面碾压** —— 它的平滑度（92.7）**不如**
   `saliency_smooth`（69.9）。但后者**不感知速度约束**，角速度合规
   仅 58%、峰值 57°/s（超出配置上限）。其"更平滑"是以牺牲运动
   可控性换来的。`ours` 在合规上领先 25 个百分点。

### 4.3 消融实验

计划中的三个关键消融：

| 消融 | 预期 | 状态 |
|---|---|---|
| yaw 边界处理开/关 | 跨边界序列上提升显著，不含边界序列上无差别 | ✅ 由 `test_tracking_spherical.py` 的对照组覆盖 |
| 球面距离 vs 像素距离 | 高纬场景差异显著 | ✅ 由 `test_geometry_region.py` 覆盖 |
| 有 / 无 LLM 规划 | — | ⚠️ **未完成**（见 §5.4） |

**第一个消融的对照组设计**值得说明：测试中同时实现了"朴素做法"
（wrap 后直接相减），证明它确实会失败（假距离 358° vs 真实距离 2°）。
**这是为了避免"在解决一个伪问题"** —— 必须先证明问题真实存在。

### 4.4 端侧性能实测

| 模型 | 峰值显存 | 延迟 |
|---|---|---|
| YOLO11n @640×1280 | 64.7 MiB | 12.4 ms |
| YOLO11s @640×1280 | 97.2 MiB | 17.5 ms |
| 实例提取（纯 CPU） | 0 | 262 ms |

端到端（30 帧）：

```
实例提取 0.37s | 球面跟踪 5.85s | 场景图 0.02s
剪辑规划 0.04s | 轨迹优化 0.21s | 渲染 4.39s
                                      总计约 11-15 秒
```

**诚实对比**：Insta360 端侧做到 1-2ms/帧。但那是**专用 4nm NPU +
更小的输入分辨率**，本项目是通用 GPU 上的通用方案，量级差异合理。

## 5. 讨论

### 5.1 一个未解决的构图问题

跑多素材对比时发现：对于某些素材（如 `panorama_0`），系统会选一个
**巨大的近距离主体**作为拍摄对象，相机贴近它导致画面被占满，
观感很差。

**根因**：主体选择只依据「显著性 + 尺寸」，缺审美判断。系统不知道
"贴近大楼墙面拍的画面很难看"。

**改进方向**：把构图质量**显式建模**进目标函数 —— 例如惩罚主体的
角尺寸过大、限制最近拍摄距离、或引入"画面内容多样性"指标。

**这类局限应写进报告而非藏起来**，因为它指向了真实的改进空间。

### 5.2 三次「拿错尺子」

这是本项目最值得记录的经验：

| # | 错误 | 后果 | 发现方式 |
|---|---|---|---|
| 1 | 用像素距离衡量球面量 | 高纬目标构图质量被系统性高估 | 理论分析 |
| 2 | 用 jerk（三阶差分）衡量二阶优化目标 | 量纲随帧率变化、与目标不一致 | **扫 max_iter 200→4000 结果完全一样** |
| 3 | 用整条拼接轨迹衡量连续运动 | **把「切镜」算成「剧烈运动」**，峰值虚高 49 倍 | 跑多素材对比时指标异常 |

**第 3 个最有代表性**：指标显示峰值 2195°/s 而配置上限 45°/s，
第一反应是"求解器失控了"。但**连续扫 `max_iter` 从 200 到 4000
结果完全相同**——这个反常现象提示该怀疑的不是优化器。

修正后峰值是 **46°/s**，**正好贴着配置的 45°/s 上限**，说明约束
一直在正常工作。

**教训**：当优化器"看起来没效果"时，先怀疑指标是否量错了对象。

### 5.3 关于「不用框架」的取舍

三个刻意的不使用：

1. **不用 LangGraph/AutoGen** —— 本任务是单链路（读 PSG → 思考 → 输出
   DSL），没有多智能体协商或循环图。框架会带来额外抽象层与不可控的
   token 开销。实际实现是一个 30 行的 while 循环 + pydantic 校验。

2. **不用 Celery/Redis** —— 任务是单机串行的（一块 GPU、一次一个视频）。
   分布式能力在此毫无用武之地。FastAPI 的 `BackgroundTasks` 足够。

3. **前端不用 React + Vite** —— Demo 的价值在于**能被立刻打开看**。
   构建流程意味着演示前要先 `npm install`，任何一步失败都看不到东西。

共同标准：**让系统能被真正跑起来**。这不是"拒绝使用成熟工具"，
而是拒绝为不需要的复杂度付费——若日后需求真的出现（多用户、
持久化、复杂交互），会带着真实约束去选型，而非凭"生产环境都这么做"
的想象。

## 6. 局限

**必须明确声明的**：

1. **无真实视频验证** —— 数据集是静态全景图，跟踪质量在合成序列上
   验证。真实视频的动态特性（运动模糊、编码伪影、相机抖动）未覆盖。

2. **无 Pano2Vid 的 DTW 对比** —— 该数据集（唯一的人工运镜 GT）链接
   未能获取，因此轨迹质量只用了可自洽计算的指标。

3. **显著性为弱监督** —— 无语动仪 GT，用语义 mask 前景类作代理。
   这不是真正的显著性标注。

4. **LLM 规划的 A/B 未做** —— Demo 默认走纯优化器降级路径。
   真实 LLM 通路已实现且有 24 项测试覆盖，但未做有/无 LLM 的
   成片质量对比。

5. **主体选择缺审美判断** —— 见 §5.1。

---

## 7. 结论

本文介绍了 PanoDirector 的设计与实现。三条主要贡献：

1. **球面几何的系统性原则**：周期量的处理应发生在数据边界，
   本项目在四处独立应用了这一原则

2. **LLM 的约束输出范式**：通过类型系统（而非 prompt 工程）强制
   LLM 只输出可校验的约束

3. **评测优先的方法论**：三次「拿错尺子」的经历说明，在全景视觉
   这类缺少公认指标的领域，「怎么衡量」与「怎么做」同等重要

**代码与可复现性**：8508 行源码、533 项测试全部通过、
所有实验数字可通过 `scripts/run_benchmark.py` 复现。
